Odoo Hackathon 2026 · Team of 4 · 6 Hours

AssetFlow — build plan & module split

Enterprise Asset & Resource Management System. Four full-stack developers, four independent verticals, one locked schema. This is the single source of truth for who builds what.

Next.js frontend FastAPI / Python PostgreSQL local 6h budget
Golden rule for independence: lock the DB schema and API contract in the first 45 minutes. After that, each person only touches their own folders. The only two shared imports everyone uses are the auth dependency and the notify() helper — both finished before parallel work begins, so nobody waits.

Folder-per-owner = near-zero merge conflicts

backend/app/
  core/          # P1: db.py, auth.py, config.py, deps.py
  models/        # one file per module: org.py, assets.py, ops.py, insight.py
  modules/
    org/         # P1      assets/    # P2
    ops/         # P3      insight/   # P4  (+ notifications helper)
  main.py        # P1: registers all routers
frontend/app/
  (auth)/ org/   # P1      assets/    # P2
  ops/           # P3      audit/ dashboard/ reports/ activity/   # P4
  components/ui/ # SHARED — built in Phase 0, then FROZEN
  lib/api.ts     # SHARED — fetch wrapper + auth token

You only edit files inside your own folders. Shared folders (core/, components/ui/, lib/api.ts) are built in Phase 0 and frozen — changes need a team ping.

04 The Logic Judges Look For

Build these as DB-backed logic, not just UI checks

1

No double-allocation

An asset may have only one allocations row with status='active'. If someone tries to allocate a held asset, block it, show "currently held by <name>", and offer a Transfer Request button.

2

No booking overlap

Reject a new booking unless new.end <= existing.start OR new.start >= existing.end for the same resource. 9:00–10:00 booked → 9:30–10:30 rejected, 10:00–11:00 accepted.

3

Automatic status transitions

Maintenance approved → asset under_maintenance; resolved → available. Audit close → confirmed-missing item → asset lost. Overdue allocation auto-flagged past return date.

05 Timeline · 360 Minutes

Together, then fully parallel, then integrate

0:00 – 0:45 · FOUNDATION (all together)

Lock the schema, ship the shared plumbing

  • P1: repo scaffold, Postgres, FastAPI, auth (signup/login/JWT), get_current_user + require_role deps.
  • P4: notify() + log_activity() helpers + their tables — ship as importable functions.
  • P2 & P3: write models against the schema, seed data, build the frozen components/ui shell.
  • ALL: finalize schema + API contract. Do not leave this phase until the schema is locked.
0:45 – 4:30 · PARALLEL VERTICALS (independent)

Each person: models → API → UI, own folders only

  • Only dependencies are require_role (P1) and notify() (P4) — already done.
  • Commit every ~30 min. Aim for 8–12 commits each.
4:30 – 5:15 · INTEGRATION

Merge to main, wire the dashboard

  • P1 reviews & merges branches. P4 wires dashboard KPIs to real data via API.
  • Connect nav links between modules.
5:15 – 6:00 · POLISH + DEMO PREP

Validation pass, seed the demo story, rehearse

  • Seed one clean story: register → allocate → maintenance → approve → resolve → return → audit.
  • Every form + endpoint validated. Everyone rehearses their segment.
